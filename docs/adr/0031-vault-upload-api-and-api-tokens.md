# ADR-0031 — آپلود Vault روی سرور و توکن دسترسی برنامه‌ای

**وضعیت:** پذیرفته‌شده
**تاریخ:** ۱۴۰۵
**مرجع:** ADR-0030 بند ۳ · ADR-0001 (استقرار روی زیرساخت ایران) · PRD §13.2 فاز ۳

---

## زمینه

ADR-0030 `publish_notes` را از دیسک جدا کرد تا «مسیر آپلود» بعداً همان را صدا بزند. در استقرار
واقعی سایت روی سرور ایران است و Vault روی رایانهٔ مالک؛ `vault publish` به دیتابیس سرور
نمی‌رسد (و نباید برسد: پورت PostgreSQL را به اینترنت باز نمی‌کنیم).

## تصمیم‌ها

### ۱. `POST /api/v1/vault/publish` — متن خام، نه نتیجهٔ تحلیل

بدنه فهرست `{path, raw}` است، `raw` متن کامل فایل. **سرور خودش تحلیل می‌کند**
(`parse_files` ← `publish_notes`)، نه ابزار مالک. دلیل: یک منبع حقیقت برای قواعد
اعتبارسنجی، و نبود راهی برای ابزار که ردیفی با `access` یا `status` دست‌کاری‌شده بنویسد.
`sha256` از همان `raw` می‌آید، پس انتشار محلی و از راه دور روی یک Vault یک نتیجه می‌دهند
(اجرای دوباره = هیچ نوشتنی).

- `apply` پیش‌فرض `false` است: **پیش‌نمایش**. (همان قاعدهٔ ADR-0030.) پیش‌نمایش در یک
  SAVEPOINT اجرا و برگردانده می‌شود، نه کل نشست؛ ثبت `last_used_at` توکن در هر دو حالت می‌ماند.
- `complete` پیش‌فرض `false`: **فقط وقتی ابزار بگوید «این کل Vault است» فایل ناپدیدشده
  آرشیو می‌شود.** فهرست ناقص (مثلاً یک آپلود دستی) هرگز آرشیو نمی‌کند. `vault push` هنگام نبودِ
  پوشهٔ `12_Content` `complete=false` می‌فرستد (همان محافظت «دیسک وصل نیست»).
- `client_errors`: فایلی که ابزار نتوانست بخواند (غیر UTF-8) هم خطاست و هم **آرشیو نمی‌شود**.
- مسیر باید `12_Content/…​.md` باشد؛ فایل‌ها و پوشه‌های `_…` و `.…` مثل دیسک نادیده‌اند.
- سقف: ۵۰۰ یادداشت و ۳۰۰٬۰۰۰ نویسه برای هر یادداشت (۴۲۲). سقف nginx
  (`client_max_body_size 64m`) از بدنهٔ بیشینه بزرگ‌تر است.
- هر انتشار واقعیِ تغییردار یک ردیف حسابرسی `CONTENT_PUBLISHED` می‌نویسد.

### ۲. توکن دسترسی برنامه‌ای (PAT)، نه ورود با OTP

`vault push` آدمی پشتش نیست که OTP بگیرد و JWT ۱۵ دقیقه‌ای هم بی‌معنی است. جدول `api_tokens`:

- متن `silp_pat_<۴۳ نویسه>`، **فقط یک‌بار** هنگام ساخت نمایش داده می‌شود؛ در دیتابیس فقط
  `sha256` (توکن ۲۵۶ بیتی تصادفی است، هش کند لازم نیست) و چهار نویسهٔ آغازین برای شناسایی.
- **دامنه‌دار** (`vault:publish`): سقف را پایین می‌آورد، نه بالا. توکن هرگز بیش از مجوزهای
  *همین لحظهٔ* صاحبش نمی‌دهد: ادمینی که نقشش گرفته شد، توکنش همان لحظه ۴۰۳ می‌شود
  (تست دارد). مجوز تازهٔ `content.publish` فقط `ADMIN` است.
- **قابل ابطال و انقضادار**. ابطال‌شده، منقضی و ناشناخته هر سه یک `۴۰۱` می‌دهند تا کسی
  توکن باطل را از نادرست تشخیص ندهد.
- **جدا از نشست وب:** JWT مرورگر روی این مسیر `۴۰۱` است و توکن برنامه‌ای روی مسیرهای دیگر
  کار نمی‌کند (وابستگی `require_token`). توکن دزدیده‌شدهٔ یک ابزار به نشست وب گره نمی‌خورد.
- ساخت و ابطال **فقط از CLI روی سرور** (`python -m silp.scripts.api_token create|list|revoke`)،
  نه از API: کسی که به سرور شل دارد از قبل همه‌چیز دارد و سطح حملهٔ تازه‌ای باز نمی‌شود.
  CLI می‌سنجد صاحب توکن مجوز انتشار را دارد.

### ۳. `vault push`

`python -m silp.scripts.vault push [--apply] [--keep-missing]` با `SILP_API_URL` و
`SILP_API_TOKEN` (توکن عمداً **پارامتر خط فرمان نیست**، تا در تاریخچهٔ shell نماند).
به دیتابیس نمی‌رسد و تنظیمات سرور (`DATABASE_URL`، کلیدها) نمی‌خواهد. نشانی غیر `https`
(جز `localhost`) رد می‌شود، چون توکن در هدر می‌رود.

## پیامدها

**مثبت** — Vault روی رایانهٔ مالک می‌ماند و سایت روی سرور ایران به‌روز می‌شود، بی‌باز‌کردن
پورت دیتابیس. رفتار انتشار یکی است (یک `publish_notes`).

**منفی / ریسک باقی‌مانده**

- سرور توکن را هش می‌کند اما هیچ محدودیت نرخی روی مسیر نیست؛ ۲۵۶ بیت بی‌نیاز از آن می‌کند، ولی
  حجم بدنه را nginx محدود می‌کند.
- **`export` و `broadcast` هنوز به دیتابیس می‌رسند** (آینهٔ سایت ← Vault و پیام گروهی). از راه
  دور هنوز کار نمی‌کنند؛ صندوق درخواست‌ها را داشبورد مالک (ADR-0032) پوشش می‌دهد. دامنهٔ
  `vault:read` و `vault:broadcast` برای فاز بعد است.
- توکن روی رایانهٔ مالک در متغیر محیطی می‌ماند؛ رایانهٔ آلوده = توکن آلوده. ابطال یک دستور است.
