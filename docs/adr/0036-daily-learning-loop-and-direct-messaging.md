# ADR-0036 — حلقهٔ یادگیری روزانه، مهارت‌محوری و پیام‌رسانی استاد–دانشجو

**وضعیت:** پیشنهاد (منتظر تأیید مالک؛ هیچ کدی هنوز نوشته نشده)
**تاریخ:** ۱۴۰۵/۰۷/۱۳
**مرجع:** ADR-0010 · ADR-0011 · ADR-0013 · ADR-0020 · ADR-0021 · ADR-0028 · ADR-0035

---

## ۰. وضع موجود (حقیقت‌سنجی پیش از طراحی)

«هیچ درس و پروژه‌ای قابل تعریف نیست» **باگ نبود؛ دیتابیس توسعه خالی بود** (۰ درس، ۰ ارائه، ۰ پروژه).
با `seed` + `sync_courses` + `import_roster` پر شد: ۵ درس، ۵ ارائه، ۲۵ پروژهٔ نمونه، و فهرست
دانشجویان دو درس (ترابری ۲۷ نفر، ایمنی راه ۲۵ نفر). سه درس دیگر هنوز فهرست ندارند.

آنچه **از قبل ساخته شده** و نباید دوباره ساخته شود:

| نیاز شما | وضع |
|---|---|
| پنجرهٔ زمانی آزمون و مدت‌زمان مستقل | ✅ `quizzes.opens_at/closes_at` و `duration_min` |
| بانک سؤال، تصادفی‌سازی سؤال و گزینه | ✅ `question_bank`, `shuffle_*` |
| تحلیل آزمون (آلفا، ضریب تمایز، توزیع گزینه) | ✅ ADR-0028 |
| امتیاز، نشان، رتبه | ✅ ADR-0012/0024 |
| اعلان همگانی به کل درس | ✅ `announcements` (یک‌طرفه) |
| کانال‌های اعلان (ایمیل، پیامک، تلگرام، ایتا، واتساپ، Push) | ✅ outbox، ADR-0013 |
| فهرست دانشجوی هر درس و فعال‌سازی حساب | ✅ ADR-0035 |

**آنچه نیست** (موضوع این سند): سلسلهٔ Course→Module→Lesson، زنجیرهٔ سؤال→Topic→Concept→Skill،
تشخیص مهارت، حلقهٔ «امروز چه بخوانم»، استمرار (Streak)، حالت آزمون/مرور، و **گفت‌وگوی دوطرفه
با دانشجو** (تلگرام جایگزین).

## ۱. نقد فرضیات (صریح)

1. **«سامانهٔ آزمون نمی‌سازم»، ولی مدل فعلی آزمون‌محور است.** درست است؛ `Quiz` امروز یک رویداد
   نمره‌دار است. باید یک «چک‌پوینت» سبک و بی‌نمره‌ی-سنگین کنارش بنشیند، نه جایگزینش. آزمون
   میان‌ترم/پایان‌ترم هنوز لازم است (نمرهٔ رسمی). **پس دو نوع ارزیابی، یک موتور.**
2. **تبدیل صورت سؤال به عکس را رد می‌کنم.** (جزئیات §۴) اثر امنیتی‌اش ناچیز است (OCR و Lens در
   ثانیه می‌خوانند)، ولی هزینه‌اش واقعی است: دسترس‌ناپذیر برای صفحه‌خوان، فارسی/RTL در Canvas
   شکننده، حجم، موبایل کند، و سؤال‌های فرمول‌دار بدتر.
3. **«جلوگیری از کپی» را هدف نکنید؛ «بی‌ارزش کردن کپی» را هدف بگیرید.** سؤال‌های متغیر
   (عددها و سناریو از قالب ساخته می‌شوند) + بانک بزرگ + زمان کوتاه، بیشتر از هر قفل ظاهری کار می‌کند،
   چون پاسخِ هوش مصنوعی به نسخهٔ شخصی همان دانشجو برای دیگری غلط است.
4. **«هر روز یک آزمون» برای کل دانشجویان خسته‌کننده می‌شود** اگر اجباری و نمره‌دار باشد. استمرار
   باید با پاداش بیاید، نه جریمه. نمرهٔ درس را فقط آزمون‌های رسمی بسازند؛ چک‌پوینت روزانه فقط XP
   و مهارت بسازد (و حداکثر یک سهم کوچک و اختیاری در «نمرهٔ مشارکت»).
5. **Monta فقط ایده است** — موافقم؛ مدل داده و UI از نو.
6. **مهارتِ «سطح» از ۵ سؤال قابل‌اعتماد نیست.** برآورد مهارت باید بیزی/میانگین متحرک با وزن
   زمان باشد و تا «حداقل N پاسخ» برچسب «کم‌داده» بخورد؛ وگرنه نقشهٔ مهارت دروغ می‌گوید.

## ۲. معماری محصول

### ۲.۱ زنجیرهٔ محتوا

```
Course ─► Module ─► Lesson ─► (Reading | Quiz[Checkpoint])
```

- `CourseWeek` امروز «هفته» است؛ **Module = گروه‌بندی اختیاری هفته‌ها** (ستون `module_id` روی
  هفته)، نه جدول جدا از صفر. درس‌های روزانه در `Lesson` می‌نشینند (زیر هفته).
- `Lesson`: عنوان، متن Markdown (یا ارجاع به `content_items` مخزن Vault/مطالب)، تاریخ انتشار،
  زمان مطالعهٔ تخمینی، وضعیت (پیش‌نویس/منتشر).
- هر Lesson صفر یا چند `Checkpoint` دارد؛ همان `Quiz` با `kind='CHECKPOINT'`.

### ۲.۲ زنجیرهٔ دانش (برای تشخیص مهارت)

```
Skill (سطح بالا: «تحلیل ظرفیت»)
  └─ Concept («HCM — سطح سرویس»)
       └─ Topic (سرفصل درس)
            └─ Question
```

سؤال به **Concept** وصل می‌شود؛ Concept به یک Skill (و Topic). چون Skill موجود (`skills`) برای
پرسشنامهٔ مهارت دانشجو (Excel، Python، …) است، **جدول جدا `competencies`** می‌سازیم تا
مهارت‌های «عمومی پروفایل» با «شایستگی‌های درسی» قاطی نشوند. رأی‌گیری از شما: نام فارسی «شایستگی».

### ۲.۳ نوع‌های ارزیابی (یک موتور)

| نوع | هدف | نمره رسمی | پنجره | مدت | سؤال |
|---|---|---|---|---|---|
| Checkpoint (روزانه) | تمرین و تشخیص | ❌ (XP) | چند ساعت | ۵–۱۰ دقیقه | ۵–۱۵ از استخر |
| Quiz هفتگی | بازبینی | اختیاری | چند روز | ۳۰ دقیقه | ۲۰ |
| Exam (رسمی) | نمره | ✅ | ثابت | ثابت | ثابت/تصادفی |

نام در UI: **«چالش امروز»** برای Checkpoint (کوتاه، غیرتهدیدی)، «آزمون» فقط برای رسمی. معایب نام
جدید: دانشجو فکر می‌کند اهمیتی ندارد؛ راه‌حل: بازخورد مهارتی همان‌جا نشان داده می‌شود، و XP/استمرار
جدی گرفته می‌شود. (نام داخلی کد: `checkpoint`.)

### ۲.۴ پیام‌رسانی (جایگزین تلگرام)

امروز فقط «اعلان همگانی» یک‌طرفه داریم. نیاز: همه، گروه، تک‌نفر، **با امکان پاسخ**.

- **Conversation** با سه نوع: `OFFERING` (کانال درس، فقط استاد می‌نویسد؛ دانشجو واکنش/سؤال)،
  `GROUP` (زیرگروه یا تیم پروژه)، `DIRECT` (استاد↔یک دانشجو، دوطرفه).
- **Message** با پیوست، وضعیت «دیده شد»، و پاسخ‌به. تحویل روی outbox موجود سوار می‌شود: درون‌برنامه
  (اصلی) + Push + ایمیل + ایتا/تلگرام برای «یک اعلان کوتاه که بیا سایت». **محتوای گفت‌وگو در
  پیام‌رسان بیرونی نمی‌رود** (خصوصی و قابل‌ردیابی ماندن).
- استاد از صفحهٔ دانشجو (`teach/offerings/[id]/students`) با یک کلیک گفت‌وگوی مستقیم باز می‌کند؛
  «ارسال به همه / بخش انتخابی / فقط آن‌ها که چالش امروز را نداده‌اند» از همان‌جا.
- دانشجو فقط با **استاد و دستیارِ درس‌های خودش** گفت‌وگو می‌کند، نه با هر کاربر (کاهش آزار و اسپم؛
  نرخ‌محدودی دارد).
- گزارش «چه کسی نخوانده» برای استاد (چیزی که تلگرام نداشت).

## ۳. UX

داشبورد دانشجو = **«امروز»**، نه فهرست بخش‌ها. موافقم با ایدهٔ شما و تقویتش می‌کنم:

```
امروز چه بخوانم؟   ← درس‌نامهٔ امروز (۶ دقیقه)
        ↓
چالش امروز         ← ۸ سؤال، ۷ دقیقه، تا ۲۲:۰۰
        ↓
بازخورد            ← «قوی: جریان ترافیک · ضعیف: ظرفیت» + توضیح هر پاسخ
        ↓
پیشنهاد بعدی       ← مرور ۲ مفهوم ضعیف (فاصله‌دار) یا درس فردا
```

نقد: اگر فقط همین باشد، دانشجوی «می‌خواهم یک درس را کامل ببینم» گم می‌شود؛ پس صفحهٔ درس (فهرست
هفته/ماژول) باقی می‌ماند و «امروز» فقط **ورودی پیش‌فرض** است. اگر امروز چیزی منتشر نشده: «مرور
فاصله‌دار» یا مفهوم ضعیف نشان داده می‌شود تا صفحه هرگز خالی نباشد.

**Exam Mode:** تمام‌صفحه، یک سؤال در صفحه، تایمر، بدون منو. **Review Mode:** پاسخ درست، توضیح،
قابل کپی، پیوند به درس‌نامه، «این مفهوم را مرور کن». دو کامپوننت جدا، نه یک کامپوننت با پرچم.

## ۴. جلوگیری از کپی ساده — تحلیل و پیشنهاد نهایی

| روش | مزیت | عیب | حکم |
|---|---|---|---|
| تبدیل سؤال به عکس | متن مستقیم کپی نمی‌شود | OCR/Lens خنثی‌اش می‌کند؛ ناپایدار در RTL؛ دسترس‌ناپذیر؛ حجم | ❌ |
| Canvas rendering | کپی متن نه | همان OCR؛ فارسی/ترکیب حروف خراب؛ هزینهٔ CPU موبایل | ❌ |
| SVG متنی | مقیاس‌پذیر | متنش هنوز انتخاب‌پذیر/DOM | ❌ |
| غیرفعال‌کردن select/copy/contextmenu | ارزان، جلوی کپی اتفاقی | با DevTools/اسکرین‌شات دورزدنی | ✅ (لایه نرم) |
| واترمارک پویا (نام + شمارهٔ دانشجو، کم‌رنگ) | بازدارندهٔ اجتماعی؛ ردیابی نشت | زیبایی؛ فقط بازدارنده | ✅ |
| Partial image (فقط شکل/نمودار/جدول تصویر) | محتوایی که واقعاً تصویر است | سؤال متنی را محافظت نمی‌کند | ✅ فقط برای شکل‌ها |
| رندر سمت سرور (HTML شخصی‌شده) | سؤال هر نفر متفاوت | پیچیدگی | ✅ هسته |
| استخر + تصادفی‌سازی | پاسخِ کپی‌شده برای دیگری غلط | نیاز به سؤال بیشتر | ✅ هسته |
| **سؤال پارامتری** (عدد/سناریوی ساخته‌شده از قالب) | پاسخ AI-کپی‌شده فقط برای همان نسخه | سازندگی سخت‌تر | ✅✅ بهترین اهرم |
| مدت کوتاه + زمان‌سنجی سمت سرور | فرصت پرسیدن از AI کم | دانشجوی کند ناراضی | ✅ |
| تشخیص خروج از تب (ثبت، نه مجازات) | داده برای استاد | حریم خصوصی، مثبت کاذب | ✅ فقط ثبت و نمایش |

**راهکار نهایی:** HTML شخصی‌شده از سرور + نبود select/copy در Exam Mode + واترمارک پویا + استخر +
سؤال پارامتری + تایمر سرور + ثبت رخداد تب. بدون تصویرسازی متن. پیشنهاد اولیهٔ شما (HTML + قفل +
Canvas overlay + واترمارک + استخر + تصادفی) را تأیید می‌کنم **به‌جز Canvas overlay**، که ارزشی
نمی‌افزاید و فارسی را می‌شکند؛ واترمارک را خودِ DOM/CSS می‌گذاریم. اعتراف صادقانه: بازدارندهٔ
اجتماعی و بی‌ارزش‌سازی (پارامتری) اصل کار است، نه قفل فنی.

پس از پایان تلاش (`submitted`) Review Mode همه‌چیز را باز می‌کند. در طول پنجره (که دیگران هنوز
نداده‌اند) پاسخ درست فقط **بعد از بسته‌شدن پنجرهٔ همان چالش** نشان داده می‌شود، وگرنه به همکلاسی
لو می‌رود؛ دانشجو فوراً فقط «درست/غلط + مهارت» می‌بیند و توضیح کامل با تأخیر.

## ۵. مدل داده (افزوده‌ها؛ هیچ جدول موجود حذف نمی‌شود)

```
modules(id, course_id, title, sort_order)
course_weeks.module_id  NULL  → modules
lessons(id, offering_id, week_id NULL, module_id NULL, title, body_md,
        content_item_id NULL, est_minutes, publish_at, status)

competencies(id, code UNIQUE, title_fa, domain)               -- شایستگی
concepts(id, competency_id, topic_id NULL, code UNIQUE, title_fa)
topics(id, course_id, title_fa, sort_order)

question_bank.concept_id NOT NULL(برای سؤال‌های تازه)  → concepts
question_templates(id, bank_item_id, param_spec jsonb)        -- سؤال پارامتری
question_bank.version / retired_at                            -- نسخه‌بندی؛ سؤال منتشر ویرایش نمی‌شود

quizzes.pool_size, quizzes.draw_count                         -- n سؤال از استخر

quiz_attempts.focus_events jsonb                              -- خروج از تب (فقط ثبت)

competency_mastery(user_id, competency_id, score 0..1, evidence_n, updated_at)
   -- از quiz_answers با میانگین متحرک؛ evidence_n<5 ⇒ «کم‌داده»
streaks(user_id, offering_id, current, longest, last_day)
review_schedule(user_id, concept_id, due_on, interval_days)   -- مرور فاصله‌دار (v2)

conversations(id, kind, offering_id NULL, title, created_by)
conversation_members(conversation_id, user_id, role, last_read_at)
messages(id, conversation_id, sender_id, body, reply_to NULL, created_at, deleted_at)
message_attachments(message_id, file_id)
```

`competency_mastery` و `streaks` **مشتق‌اند**؛ منبع حقیقت `quiz_answers` است و بازسازی‌پذیرند.
هر سؤال شناسهٔ مفهوم را هنگام پاسخ در `quiz_answers` منجمد می‌کند (الگوی ADR-0007) تا ویرایش
بعدیِ نقشه تاریخچه را تغییر ندهد.

استخر چندهزارسؤالی: ایندکس روی `(concept_id, difficulty)`؛ انتخاب سؤال با `seed` ثابت و قابل‌بازتولید؛
سؤال با `usage_count` و آمار ADR-0028 بازنشسته یا اصلاح می‌شود.

## ۶. امتیاز و استمرار

- «چالش امروز کامل شد» +XP پایه (مستقل از نمره).
- Streak ۷ و ۳۰ روزه پاداش پلکانی؛ **یک «روز معافیت» در هفته** (freeze) تا یک بیماری استمرار را
  نابود نکند (در غیر این صورت ترک‌کننده‌ها زیاد می‌شود).
- «بهبود مهارت» (افزایش `competency_mastery` از آخرین سنجش) +XP؛ نمرهٔ بالا فقط پاداش کوچک.
- پاداش‌ها فقط **یک بار به‌ازای هر چالش** و با سقف روزانه (جلوگیری از اسپم‌گرفتن XP). از
  موتور قوانین امتیاز موجود (`point_rules` قابل‌ویرایش توسط مدیر) استفاده می‌شود، نه ثابت کد.

## ۷. MVP و نقشهٔ راه

**MVP (اولین چیزی که واقعاً به کلاس می‌رود):**
1. درس/ارائه/دانشجو از UI **و** اکسل (انجام شد برای ۲ درس؛ ۳ درس دیگر: فهرست از شما).
2. گفت‌وگوی مستقیم و کانال درس (§۲.۴) — **اولویت اول چون جایگزین تلگرام است**.
3. `Lesson` + `Checkpoint` (۵–۱۵ سؤال، پنجره + مدت) روی موتور موجود، Exam Mode / Review Mode،
   واترمارک، استخر + تصادفی.
4. `concepts/competencies` و برچسب‌گذاری سؤال (یک `Concept` الزامی برای سؤال تازه).
5. داشبورد «امروز» + XP + Streak.

**v2:** نقشهٔ مهارت و پیشنهاد مرور فاصله‌دار؛ سؤال پارامتری؛ ورود گروهی سؤال از فایل؛
گزارش نخواندگان؛ تحلیل «ضعف کلاس» برای استاد (کدام مفهوم باید فردا تدریس شود).
**v3:** تشخیص مهارت تطبیقی (CAT)، اتصال شایستگی‌ها به پیشنهاد پروژه/پژوهش (مهارت→پروژه)،
چندحوزه‌ای، یادآور هوشمند ایتا/تلگرام.

## ۸. ریسک‌ها

| ریسک | کاهش |
|---|---|
| زمان استاد برای نوشتن روزانه درس و سؤال زیاد است | ورود دسته‌ای (Markdown/اکسل)، پیش‌نویس با کمک هوش مصنوعی ولی **بازبینی انسانی**، قالب سؤال پارامتری |
| برچسب Concept برای هزاران سؤال خسته‌کننده است | پیشنهاد خودکار برچسب + تأیید استاد؛ بدون Concept سؤال منتشر نشود |
| نقشهٔ مهارت با داده کم گمراه‌کننده است | برچسب «کم‌داده»، حداقل شاهد، نمایش بازه نه عدد دقیق |
| پیام‌رسانی = آزار/اسپم/مسئولیت حقوقی | فقط ارتباط استاد/دستیار↔دانشجوی همان درس، گزارش و حذف نرم، لاگ حسابرسی |
| ایتا/تلگرام فیلتر یا قطع می‌شود | اصلِ گفت‌وگو درون‌برنامه + Push؛ بیرونی فقط «اعلان کوتاه» |

## ۹. مخالفت‌ها و پیشنهادهای جایگزین (خلاصه)

- ❌ عکس‌کردن سؤال ← ✅ پارامتری + شخصی‌سازی سرور.
- ❌ Canvas overlay ← ✅ واترمارک DOM.
- ⚠️ «آزمون» نباید یکسره حذف شود؛ سه نوع ارزیابی با یک موتور.
- ⚠️ داشبورد «امروز» ورودی پیش‌فرض است، نه جایگزین صفحهٔ درس.
- ➕ پیام‌رسانی دوطرفه از ابتدا در MVP (نیاز واقعی فوری شما).
- ➕ پاسخ درست تا بسته‌شدن پنجره پنهان می‌ماند (جلوگیری از نشت به همکلاسی).

## ۱۰. تصمیم‌های لازم از مالک

1. تأیید ترتیب MVP (پیام‌رسانی اول؟).
2. نام فارسی «چالش امروز» برای Checkpoint و «شایستگی» برای Competency.
3. آیا چالش روزانه سهمی در نمرهٔ درس داشته باشد؟ (پیشنهاد: خیر؛ حداکثر «مشارکت» اختیاری.)
4. فهرست دانشجوی سه درس باقی‌مانده (فایل اکسل).
5. زمان دیپلوی هدف (برای تنظیم ترتیب: امنیت/پشتیبان‌گیری پیش از ویژگی‌های v2).
