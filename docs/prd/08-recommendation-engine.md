# ۰۸ — موتور توصیه‌گر

**هدف:** به هر دانشجو نشان دهیم کدام پروژه‌ها به او می‌خورند و **چرا**.

**اصل راهنما (D-10):** الگوریتم قطعی، قابل توضیح و قابل تست است. نه یادگیری ماشین.
دلیل: دادهٔ تاریخی نداریم، و مهم‌تر — دانشجو باید بتواند بفهمد و با تغییر نیمرخش،
نتیجه را تغییر دهد. جعبهٔ سیاه اینجا ضد هدف محصول است.

## ۸.۲ زیرامتیاز ۱ — تطابق مهارت (`S_skill`)

مهم‌ترین مؤلفه. منطق: کمبود مهارت جریمه دارد، اما مهارت اضافی پاداش کمی دارد
(چون پروژهٔ خیلی آسان هم مناسب نیست).

برای هر مهارت لازم `r` با سطح مورد نیاز `req`، وزن `w ∈ {1,2,3}`، و سطح دانشجو `u`
(اگر پاسخ نداده، `u = 1`):

```
gap = req − u

                 ⎧ 1.00                    اگر gap ≤ 0   (مهارت کافی یا بیشتر)
   fit(r)   =    ⎨ 1 − 0.25 × gap          اگر 0 < gap ≤ 2  (کمبود جزئی)
                 ⎩ max(0, 0.5 − 0.15×gap)  اگر gap > 2    (کمبود جدی)

اگر مهارت تأییدشده باشد (verified):  fit(r) = min(1, fit(r) × 1.25)
اگر مهارت is_teachable باشد:          fit(r) = min(1, fit(r) + 0.20)

               Σ w_r × fit(r)
   S_skill = ─────────────────── × 100
                  Σ w_r
```

اگر پروژه هیچ مهارت لازمی تعریف نکرده باشد: `S_skill = 70` (خنثای مثبت).

**مثال:**

| مهارت | لازم | دانشجو | وزن | teachable | gap | fit |
|-------|------|--------|-----|-----------|-----|-----|
| Python | ۳ | ۴ | ۳ | ✗ | ‑۱ | ۱.۰۰ |
| GIS | ۳ | ۲ | ۲ | ✓ | ۱ | ۰.۷۵+۰.۲۰ = ۰.۹۵ |
| نگارش | ۴ | ۱ | ۱ | ✗ | ۳ | max(0, ۰.۵−۰.۴۵) = ۰.۰۵ |

```
S_skill = (3×1.00 + 2×0.95 + 1×0.05) / (3+2+1) × 100
        = (3.00 + 1.90 + 0.05) / 6 × 100 = 82.5
```

## ۸.۳ زیرامتیاز ۲ — تطابق امکانات (`S_asset`)

امکانات فیزیکی **دروازه‌ای** هستند: نداشتن یک امکان الزامی، پروژه را عملاً
غیرممکن می‌کند. این مؤلفه برخلاف مهارت، انعطاف کمی دارد.

```
M = مجموعهٔ امکانات الزامی پروژه
P = مجموعهٔ امکانات ترجیحی پروژه
A = مجموعهٔ امکانات دانشجو

اگر M ⊄ A  ⇒  S_asset = 0  و پروژه از فهرست پیشنهاد حذف می‌شود
                              (اما در جستجوی دستی قابل دیدن است)

اگر M = ∅ و P = ∅  ⇒  S_asset = 100   (پروژه امکانات خاصی نمی‌خواهد)

در غیر این صورت:
   S_asset = 100 × (0.6 + 0.4 × |P ∩ A| / max(1, |P|))
```

> **چرا حذف کامل؟** پیشنهاد «پروژهٔ توزیع خرما» به کسی که وسیلهٔ نقلیه ندارد،
> اعتماد کاربر به موتور توصیه‌گر را از بین می‌برد. یک پیشنهاد آشکارا نامربوط،
> ارزش نُه پیشنهاد خوب را خنثی می‌کند.

## ۸.۴ زیرامتیاز ۳ — تطابق علاقه (`S_interest`)

```
I = مجموعهٔ حوزه‌های مرتبط پروژه
lvl(i) = سطح علاقهٔ دانشجو به حوزهٔ i، ۱ تا ۵ (پاسخ‌نداده = 3، خنثی)

اگر I = ∅  ⇒  S_interest = 60

           Σ_{i ∈ I} (lvl(i) − 1)
S_interest = ───────────────────── × 100
                 4 × |I|
```

تبدیل خطی: علاقهٔ ۱ ⇒ ۰، علاقهٔ ۳ ⇒ ۵۰، علاقهٔ ۵ ⇒ ۱۰۰.

## ۸.۵ زیرامتیاز ۴ — تطابق زمان (`S_time`)

```
h_u = ساعت در دسترس دانشجو در هفته (اگر نامشخص: 10)
h_p = تعهد زمانی پروژه

ratio = h_u / h_p

            ⎧ 100                        اگر 0.8 ≤ ratio ≤ 2.0
S_time  =   ⎨ 100 × (ratio / 0.8)        اگر ratio < 0.8   (وقت کم است)
            ⎩ max(60, 100 − 10×(ratio−2)) اگر ratio > 2.0  (پروژه کم‌حجم است)
```

منطق: وقت کم، جریمهٔ خطی دارد. وقت زیاد، جریمهٔ خفیف (شاید دانشجو بخواهد چند
پروژه بگیرد) و هرگز زیر ۶۰ نمی‌رود.

## ۸.۸ ترکیب و امتیاز پایه

```
وزن‌های پیش‌فرض (در app_settings قابل تنظیم):

  W = { skill: 0.30, asset: 0.20, interest: 0.20,
        time:  0.10, style: 0.10, goal:     0.10 }

base = Σ W_k × S_k          ⇒  عددی بین ۰ و ۱۰۰
```

**تعدیل وزن‌ها بر اساس کامل بودن نیمرخ:**

اگر دانشجو گام ۳ (علاقه‌ها) را پر نکرده، `S_interest` بی‌معناست. در این حالت
وزن آن مؤلفه **صفر و وزن بقیه بازنرمال** می‌شود:

```python
def effective_weights(profile, W):
    active = {k: w for k, w in W.items() if profile.has_data_for(k)}
    total = sum(active.values())
    return {k: w / total for k, w in active.items()}
```

این تضمین می‌کند دانشجویی که فقط گام ۱ را پر کرده، امتیاز ۳۰ نگیرد بلکه
امتیاز معنادار بر پایهٔ همان داده بگیرد.

## ۸.۹ ضرایب تعدیل

امتیاز پایه در ضرایب زیر ضرب می‌شود:

| ضریب | مقدار | شرط |
|------|-------|-----|
| `f_recency` | ۱.۰۵ | پروژه در ۷ روز اخیر منتشر شده |
| `f_urgency` | ۱.۰۸ | مهلت درخواست کمتر از ۷ روز مانده |
| `f_need` | ۱.۱۰ | تیم هنوز به `team_size_min` نرسیده |
| `f_course` | ۱.۱۵ | پروژه به درسی متصل است که دانشجو در آن ثبت‌نام دارد |
| `f_crowded` | ۰.۹۰ | تعداد درخواست‌های در انتظار > ۳ برابر ظرفیت باقی‌مانده |
| `f_dismissed` | ۰.۲۰ | بازخورد `NOT_RELEVANT` — «این به من نمی‌خورد» |
| `f_hidden` | ۰.۰۰ | بازخورد `DISMISSED` — «دیگر نشانم نده» (حذف کامل) |
| `f_interested` | ۱.۱۰ | بازخورد `INTERESTED` — «فعلاً نه، ولی جالب است» |
| `f_applied` | ۰.۰۰ | دانشجو قبلاً درخواست داده (از فهرست حذف) |

**معنای سه حالت بازخورد** (`recommendation_feedback.verdict` در §4.9):
`NOT_RELEVANT` تنزل شدید ولی قابل بازگشت با تغییر نیمرخ ·
`DISMISSED` حذف دائمی از پیشنهادها (همچنان در جستجوی دستی دیده می‌شود) ·
`INTERESTED` نشان‌گذاری برای بعد، با تقویت خفیف.

```
final = min(100, base × Π f_i)
```

`f_course = 1.15` عمدی است: پروژهٔ متصل به درس، هم‌زمان نمره و مهارت می‌دهد و
احتمال تکمیلش بسیار بالاتر است.

### اعمال ضرایب — ADR-0005

فرمول اولیهٔ این بند `final = min(100, base × Π f_i)` بود. اجرای واقعی روی
دادهٔ §14.5 نشان داد آن فرمول اطلاعات را از بین می‌برد: امتیاز پایهٔ
پروژه‌های مناسب بین ۹۰ تا ۱۰۰ است و حاصل‌ضرب ضرایب تا ۱.۴۳ می‌رسد، پس
`min` تقریباً همیشه فعال می‌شود و دو تا سه پیشنهاد برتر هر سه «۱۰۰٪»
می‌شوند. `MatchRing` سه حلقهٔ یکسان می‌گیرد و دانشجو هیچ ترتیبی نمی‌بیند.

**فرمول جاری:**

```
اگر هر ضریبی صفر باشد (f_hidden، f_applied)   ⇒  final = 0

s      = base × Π f⁻                     جریمه‌ها (f < 1) ضربی می‌مانند
final  = s + (100 − s) × (Π f⁺ − 1)      تشویق‌ها روی فاصلهٔ تا ۱۰۰
```

| ویژگی | چرا |
|-------|-----|
| هرگز از ۱۰۰ رد نمی‌شود | `Π f⁺ − 1 ≤ 1`، پس `final ≤ s + (100 − s)`. بدون `min`، چیزی له نمی‌شود |
| ترتیب حفظ می‌شود | اختلاف دو پایه پس از ضریب یکسان `F` برابر `(b₁−b₂)(2−F)` است و `F < 2` |
| قابل توضیح می‌ماند | «اتصال به درس، ۱۵٪ از فاصلهٔ تو تا تطابق کامل را جبران می‌کند» |

جریمه‌ها عمداً ضربی مانده‌اند: «این به من نمی‌خورد» باید امتیاز را پایین
بیاورد؛ روی هِدروم، آن را به سقف *نزدیک‌تر* می‌کرد.

**اثر روی دادهٔ واقعی** — ترتیب هیچ پرسونایی عوض نشد، فقط قابل تفکیک شد:

| پرسونا | پیش | پس |
|--------|-----|-----|
| سارا (درآمد) | ۱۰۰ · ۱۰۰ · ۸۴.۵ | ۹۷.۷ · ۹۵.۲ · ۸۴.۱ |
| امیر (مقاله) | ۱۰۰ · ۱۰۰ · ۹۴.۸ | ۹۷.۷ · ۸۹.۴ · ۸۴.۹ |

تحلیل کامل و گزینه‌های رد شده در `docs/adr/0005`.

> **نکتهٔ باز:** امتیاز پایه هنوز می‌تواند با نیمرخ ۲۵٪ کامل به ۱۰۰ برسد،
> چون §8.8 وزن‌ها را بازنرمال می‌کند. «۱۰۰٪ تطابق» از روی یک بُعد داده،
> بیش از آنچه می‌دانیم ادعا می‌کند. به §8.15 موکول شد.

## ۸.۱۱ تنوع نتایج (Diversity)

اگر ۱۰ پیشنهاد برتر همگی از یک نوع باشند، دانشجو تصویر محدودی می‌گیرد.
پس از رتبه‌بندی، **بازچینش حداکثر حاشیه‌ای (MMR-lite)** اعمال می‌شود:

```python
def diversify(ranked: list[Match], k: int = 10) -> list[Match]:
    """حداکثر ۴ پروژه از یک نوع در ۱۰ نتیجهٔ اول."""
    out, per_kind = [], Counter()
    for m in ranked:
        if per_kind[m.project.kind] >= 4:
            continue
        out.append(m); per_kind[m.project.kind] += 1
        if len(out) == k:
            break
    # اگر به k نرسیدیم، از باقی‌مانده پر کن
    if len(out) < k:
        out += [m for m in ranked if m not in out][: k - len(out)]
    return out
```

همچنین **حداقل یک پروژهٔ «کشش‌دار»** (`difficulty ≥ سطح دانشجو + 1`) در نتایج
گنجانده می‌شود، با برچسب «چالش برانگیز — اگر آماده‌ای».

## ۸.۱۲ پیاده‌سازی

### کوئری SQL (فیلتر اولیه)

فیلتر در دیتابیس، امتیازدهی در پایتون. برای مقیاس فعلی (کمتر از ۵۰۰۰ پروژه)
این بهینه است.

```sql
WITH candidate AS (
  SELECT p.id
  FROM projects p
  WHERE p.status = 'OPEN'
    AND p.deleted_at IS NULL
    AND (p.applications_close_at IS NULL OR p.applications_close_at > now())
    -- بدون درخواست قبلی
    AND NOT EXISTS (SELECT 1 FROM project_applications a
                    WHERE a.project_id = p.id AND a.applicant_id = :uid
                      AND a.status <> 'WITHDRAWN')
    -- ظرفیت باقی‌مانده
    AND (SELECT count(*) FROM team_members tm
         JOIN teams t ON t.id = tm.team_id
         WHERE t.project_id = p.id AND tm.status = 'ACTIVE') < p.team_size_max
    -- امکانات الزامی موجود باشد
    AND NOT EXISTS (
      SELECT 1 FROM project_required_assets pra
      WHERE pra.project_id = p.id AND pra.is_mandatory
        AND NOT EXISTS (SELECT 1 FROM profile_assets pa
                        WHERE pa.user_id = :uid AND pa.asset_id = pra.asset_id))
)
SELECT p.*,
       COALESCE(rs.skills, '[]'::json)    AS required_skills,
       COALESCE(ra.assets, '[]'::json)    AS required_assets,
       COALESCE(pi.interests, '[]'::json) AS related_interests
FROM candidate c
JOIN projects p ON p.id = c.id
LEFT JOIN LATERAL (…) rs ON true
LEFT JOIN LATERAL (…) ra ON true
LEFT JOIN LATERAL (…) pi ON true;
```
