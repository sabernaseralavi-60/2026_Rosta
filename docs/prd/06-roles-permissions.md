# ۰۶ — نقش‌ها و مجوزها

مدل کنترل دسترسی SILP ترکیبی از **RBAC دامنه‌دار** (نقش در یک قلمرو مشخص) و
**قواعد مالکیت** است.

## ۶.۱ نقش‌ها

| کد | عنوان | رتبه | قلمرو | توضیح |
|----|-------|------|-------|-------|
| `GUEST` | مهمان | ۰ | — | کاربر وارد نشده |
| `PUBLIC_LEARNER` | فراگیر عمومی | ۱۰ | GLOBAL | غیر دانشجو، دسترسی به دروس عمومی |
| `STUDENT` | دانشجو | ۲۰ | GLOBAL | نقش پیش‌فرض پس از ثبت‌نام |
| `PROJECT_MEMBER` | عضو پروژه | ۲۵ | PROJECT | مشتق از عضویت در تیم |
| `PROJECT_LEAD` | مدیر پروژه | ۳۰ | PROJECT | سازنده یا مسئول پروژه |
| `MENTOR` | منتور | ۴۰ | PROJECT / GLOBAL | دانشجوی ارشد یا دستیار، بازبینی تحویل‌دادنی |
| `TA` | دستیار آموزشی | ۴۵ | OFFERING | تصحیح، مدیریت محتوا، بدون نمرهٔ نهایی |
| `INSTRUCTOR` | استاد | ۵۰ | OFFERING | اختیار کامل روی ارائهٔ خود |
| `COORDINATOR` | مدیر آموزشی | ۶۰ | GLOBAL | مدیریت دروس و نیم‌سال‌ها |
| `ADMIN` | مدیر سامانه | ۹۰ | GLOBAL | دسترسی کامل به‌جز موارد ممنوع |
| `SUPPORT` | پشتیبانی | ۷۰ | GLOBAL | خواندن + جعل هویت با لاگ |

**قواعد نقش:**
- یک کاربر می‌تواند چند نقش هم‌زمان داشته باشد (استاد یک درس + دانشجوی درس دیگر).
- `PROJECT_MEMBER` و `PROJECT_LEAD` **مشتق** هستند؛ از `team_members` محاسبه
  می‌شوند و در `user_roles` ذخیره نمی‌شوند — مگر برای مدیر پروژهٔ غیرعضو.
- رتبهٔ بالاتر **به‌صورت خودکار** مجوزهای پایین‌تر را ندارد. هر مجوز صریح است.
  (این از خطاهای رایج «ادمین همه‌کاره» جلوگیری می‌کند.)

## ۶.۳ مجوزهای ممنوع برای همه

این اعمال **برای هیچ نقشی** از طریق رابط کاربری ممکن نیست:

| عمل | دلیل |
|-----|------|
| حذف یا ویرایش رکورد `audit_logs` | تمامیت حسابرسی |
| حذف یا ویرایش `point_entries` | دفتر کل تغییرناپذیر (D-09) — فقط رکورد معکوس |
| مشاهدهٔ رمز عبور یا کد OTP | هش‌شده ذخیره می‌شوند |
| مشاهدهٔ پاسخ صحیح در تلاش فعال | تمامیت آزمون |
| تغییر `started_at` یا `expires_at` یک تلاش | انصاف آزمون |
| حذف فیزیکی داده‌های دانشجو بدون فرایند رسمی | الزام نگهداری |

## ۶.۴ پیاده‌سازی

### وابستگی مجوز در FastAPI

```python
# apps/api/src/silp/core/permissions.py

class Permission(StrEnum):
    COURSE_WEEK_PUBLISH = "course.week.publish"
    PROJECT_APPLICATION_DECIDE = "project.application.decide"
    DELIVERABLE_REVIEW = "deliverable.review"
    GRADE_OVERRIDE = "grade.override"
    # …

def require(permission: Permission, scope: ScopeResolver | None = None):
    """وابستگی FastAPI که مجوز را در قلمرو مشخص بررسی می‌کند."""
    async def dependency(
        user: CurrentUser = Depends(get_current_user),
        session: AsyncSession = Depends(get_session),
        scope_id: UUID | None = Depends(scope) if scope else None,
    ) -> CurrentUser:
        if not await authz.has_permission(session, user, permission, scope_id):
            raise PermissionDenied(permission=permission)
        return user
    return dependency


# استفاده
@router.post("/deliverables/{deliverable_id}/review")
async def review_deliverable(
    deliverable_id: UUID,
    payload: ReviewIn,
    user: CurrentUser = Depends(
        require(Permission.DELIVERABLE_REVIEW, scope=project_of_deliverable)
    ),
): ...
```

### قواعد کلیدی پیاده‌سازی

۱. **هرگز در لایهٔ مسیر (router) بررسی نقش خام نکنید** (`if user.role == "ADMIN"`).
   همیشه از مجوز نام‌دار استفاده کنید. نقش‌ها تغییر می‌کنند، مجوزها پایدارترند.

۲. **بررسی مجوز در لایهٔ سرویس تکرار می‌شود** برای مسیرهایی که از کارهای پس‌زمینه
   یا CLI هم فراخوانی می‌شوند. دفاع در عمق.

۳. **فیلتر در سطح کوئری، نه پس از واکشی.** فهرست پروژه‌ها باید در SQL فیلتر شود،
   نه اینکه همه واکشی و بعد فیلتر شوند — هم کارایی، هم امنیت.

۴. **`404` به‌جای `403` برای منابع خصوصی.** اگر کاربر حق دیدن وجود منبع را ندارد،
   `404` برگردانید تا وجود آن افشا نشود. `403` فقط وقتی که وجود منبع عمومی است.

۵. **کش مجوز:** نقش‌های کاربر در Redis با TTL ۶۰ ثانیه کش می‌شوند. تغییر نقش،
   کش را فوراً باطل می‌کند.

## ۶.۵ جعل هویت (Impersonation)

برای پشتیبانی ضروری است، اما خطرناک. قواعد سخت‌گیرانه:

| قاعده | جزئیات |
|-------|--------|
| مجاز برای | `SUPPORT`، `ADMIN` |
| ممنوع روی | کاربران با نقش `ADMIN` |
| توکن | `act_as` در JWT، عمر حداکثر ۳۰ دقیقه، غیرقابل تمدید |
| نمایش | بنر قرمز دائمی: «شما در حال مشاهده به‌عنوان {نام} هستید — خروج» |
| محدودیت عمل | **فقط خواندن.** هیچ `POST`/`PATCH`/`DELETE` مجاز نیست. |
| لاگ | شروع، پایان، و **هر درخواست** در `audit_logs` با `impersonated_by` |
| اطلاع‌رسانی | کاربر هدف اعلان دریافت می‌کند: «پشتیبانی حساب شما را بررسی کرد» |

> محدودیت «فقط خواندن» تصمیم آگاهانه‌ای است: اکثر نیازهای پشتیبانی با دیدن
> رفع می‌شوند، و اجازهٔ نوشتن، مسئولیت‌پذیری را از بین می‌برد.
