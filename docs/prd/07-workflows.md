# ۰۷ — گردش‌کارها و ماشین‌های حالت

هر گذار حالت در این سند، یک تابع در لایهٔ سرویس است. **گذار غیرمجاز باید خطا
بدهد، نه اینکه بی‌صدا نادیده گرفته شود.**

## ۷.۱ ثبت‌نام و ورود اولیه

  [شروع]
     │
     ▼
 وارد کردن موبایل ──────► OTP ارسال شد
     │                        │
     │                   کد اشتباه (۳ بار) ──► چالش باطل ──► بازگشت
     │                        │

  ┌──┴──┐

  ▼     ▼
ساخت   ورود ──► onboarding_state؟

  │        ┌────┼────────────┬──────────┐
  │        │    │            │          │

### قاعدهٔ دقیق `onboarding_state`

```python
def onboarding_state(user, profile) -> str:
    if profile is None or not profile.first_name or not profile.last_name:
        return "BASIC_INFO_REQUIRED"
    if profile.survey_completed_steps < 1:       # حتی گام ۱ پر نشده
        return "SURVEY_REQUIRED"
    if profile.survey_completed_steps < 4:
        return "SURVEY_INCOMPLETE"               # قابل ادامه، مسدودکننده نیست
    return "COMPLETE"
```

| حالت | رفتار کلاینت |
|------|---------------|
| `BASIC_INFO_REQUIRED` | هدایت اجباری به `/onboarding/basic` |
| `SURVEY_REQUIRED` | هدایت به `/onboarding/survey/1` |
| `SURVEY_INCOMPLETE` | ورود آزاد + نوار دائمی «نیمرخت را کامل کن» |
| `COMPLETE` | ورود عادی |

### تولید `username`

نام کاربری برای آدرس نیمرخ عمومی (`/u/{username}`) لازم است و خودکار ساخته می‌شود:

```python
def generate_username(first: str, last: str) -> str:
    base = slugify_fa(f"{first}-{last}")          # «مریم کریمی» → "maryam-karimi"
    base = base[:28] or "user"
    for suffix in ["", "-2", "-3", ...]:          # تا ۹۹، سپس ۴ رقم تصادفی
        if not await exists(base + suffix):
            return base + suffix
```

`slugify_fa` حرف‌نویسی فارسی به لاتین انجام می‌دهد (کتابخانهٔ `python-slugify`
با نگاشت سفارشی فارسی). کاربر می‌تواند بعداً یک‌بار آن را تغییر دهد؛ تغییر
دوم نیازمند درخواست از پشتیبانی است تا لینک‌های به‌اشتراک‌گذاشته‌شده نشکنند.

**کلمات رزرو:** `admin`, `api`, `teach`, `me`, `u`, `login`, `verify`, `settings`,
`projects`, `courses`, `ideas`, `teams`, `dashboard`, `null`, `undefined`.

**قواعد:**
- `onboarding_state` توسط **سرور** محاسبه می‌شود، نه کلاینت.
- کاربر می‌تواند از گام ارزیابی رد شود (`SURVEY_INCOMPLETE` باقی می‌ماند) ولی
  داشبورد یک نوار دائمی «نیمرخت را تکمیل کن — ۲ دقیقه» نشان می‌دهد.
- برخی اقدامات نیازمند نیمرخ کامل‌اند و با `PROFILE_INCOMPLETE` رد می‌شوند:
  ارسال درخواست پروژه، ثبت کسب‌وکار.

## ۷.۲ چرخهٔ حیات ثبت‌نام در درس

```
                   ┌─────────┐
        ثبت‌نام ───►│ PENDING │
                   └────┬────┘
              تأیید استاد│ │رد استاد
                        │ └──────────► REJECTED
                        ▼
                   ┌─────────┐
                   │ ACTIVE  │◄─── ثبت‌نام بدون نیاز به تأیید
                   └────┬────┘
              انصراف    │    │  پایان ترم + نمرهٔ نهایی
             دانشجو     │    │
                        ▼    ▼
                   ┌─────────┐  ┌───────────┐
                   │ DROPPED │  │ COMPLETED │
                   └─────────┘  └───────────┘
```

| گذار | شرط | اثر جانبی |
|------|-----|-----------|
| `→ PENDING` | ارائه `OPEN` و ظرفیت آزاد و `requires_approval` | اعلان به استاد |
| `→ ACTIVE` | تأیید استاد یا عدم نیاز به تأیید | اعلان به دانشجو، دسترسی به محتوا |
| `→ DROPPED` | پیش از پایان مهلت حذف | حفظ همهٔ داده‌ها (نمرات، تلاش‌ها) |
| `→ COMPLETED` | استاد نمرهٔ نهایی ثبت کند | صدور گواهی درس (نمرهٔ ≥ ۱۰؛ اصلاح به زیر ۱۰ باطلش می‌کند)، امتیاز `LEARNING` |

> **حذف پس از مهلت:** `DROPPED` می‌شود ولی نمرهٔ نهایی صفر ثبت می‌گردد.
> این تصمیم توسط `app_settings.late_drop_policy` قابل تغییر است.

## ۷.۳ چرخهٔ حیات آزمون

### وضعیت آزمون از دید دانشجو

```
now < opens_at              ──► NOT_OPEN     «هنوز باز نشده»
opens_at ≤ now ≤ closes_at:
   تلاش فعال دارد           ──► IN_PROGRESS  «ادامه بده»
   تلاش مصرف‌شده = max      ──► EXHAUSTED    «تمام شد»
   در غیر این صورت          ──► AVAILABLE    «شروع کن»
now > closes_at             ──► CLOSED       «مهلت تمام شد»
```

### چرخهٔ حیات یک تلاش

```
   POST /quizzes/{id}/attempts
              │
              ▼
      ┌───────────────┐
      │  IN_PROGRESS  │◄──── PUT answers (هر ۱۰ ثانیه)
      └───────┬───────┘
              │
     ┌────────┼────────────────┐
     │        │                │
 ارسال    زمان تمام     ابطال توسط استاد
 دانشجو       │                │
     ▼        ▼                ▼
┌──────────┐ ┌────────────────┐ ┌────────┐
│SUBMITTED │ │AUTO_SUBMITTED  │ │ VOIDED │
└────┬─────┘ └───────┬────────┘ └────────┘
     └───────┬───────┘
             ▼
     تصحیح خودکار سؤالات بسته
             │
      ┌──────┴───────┐
      │              │
  سؤال تشریحی    بدون تشریحی
  دارد؟ بله         │
      │             │
      ▼             ▼
 ┌─────────────────────┐
 │       GRADED        │
 │ is_provisional=true │──── پس از تصحیح دستی ──► is_provisional=false
 └─────────────────────┘                              │
                                                      ▼
                                          ثبت امتیاز + اعلان نتیجه
```

**قواعد بحرانی:**

۱. **زمان‌سنج مرجع سرور است.** `expires_at` در لحظهٔ شروع محاسبه و ذخیره می‌شود.
   هر درخواست، `seconds_remaining` را از سرور برمی‌گرداند.
   فرمول دقیق: `min(started_at + duration, closes_at)` — شروع دیرهنگام
   وقت اضافه نمی‌گیرد ([ADR-0011](../adr/0011-quiz-grading-gaps.md)).

۲. **بستن خودکار:** یک کار پس‌زمینه هر ۶۰ ثانیه تلاش‌های منقضی‌شده را
   `AUTO_SUBMITTED` می‌کند. به `submit` کلاینت اتکا نمی‌شود.

۳. **پذیرش پاسخ پس از انقضا:** پاسخی که `client_ts` آن پیش از `expires_at` باشد
   و حداکثر ۳۰ ثانیه تأخیر شبکه داشته باشد، پذیرفته می‌شود. بیشتر از آن، رد.

۴. **ترتیب قطعی:** `question_order` در لحظهٔ شروع تلاش تولید و ذخیره می‌شود
   (seed = `attempt_id`). رفرش صفحه ترتیب را تغییر نمی‌دهد.
   ترتیب **گزینه‌ها** ذخیره نمی‌شود و هر بار بازمحاسبه می‌گردد، پس
   کلید مرتب‌سازی‌اش `sha256(attempt_id | question_id | option_id)`
   است نه `random` — تا به نسخهٔ پایتون گره نخورد (ADR-0011).

۵. **`auto_closed`:** هر دو مسیر ارسال به `GRADED` می‌رسند، ولی «زمانم
   تمام شد» با «ارسال کردم» یکی نیست و در ستون `auto_closed` می‌ماند.

### جریان اعتراض به نمره

```
دانشجو اعتراض ثبت می‌کند ──► OPEN ──┬── استاد می‌پذیرد ──► ACCEPTED
                                     │      └► نمره اصلاح + رکورد امتیاز معکوس + لاگ
                                     └── استاد رد می‌کند ──► REJECTED + پاسخ متنی
```
مهلت اعتراض: ۷ روز پس از انتشار نتیجه. پس از آن endpoint خطای `409` می‌دهد.

## ۷.۴ چرخهٔ حیات پروژه

```
       ┌───────┐  publish   ┌──────┐
       │ DRAFT ├───────────►│ OPEN │◄── پذیرش درخواست
       └───────┘            └──┬───┘
                               │ تیم تشکیل شد (≥ team_size_min)
                               │ یا مدیر دستی شروع کرد
                               ▼
                       ┌──────────────┐
              ┌────────┤ IN_PROGRESS  │────────┐
              │        └──────┬───────┘        │
         pause│               │ همهٔ مراحل      │cancel
              ▼               │ الزامی تأیید شد │
        ┌────────┐            ▼                ▼
        │ PAUSED │     ┌────────────┐   ┌───────────┐
        └───┬────┘     │ COMPLETED  │   │ CANCELLED │
            │resume    └────────────┘   └───────────┘
            └──────────────►
```

| گذار | شرط | اثر جانبی |
|------|-----|-----------|
| `DRAFT → OPEN` | حداقل یک مرحله تعریف شده، مهارت‌های لازم مشخص | نمایه‌سازی برای توصیه‌گر، اعلان به دانشجویان منطبق |
| `OPEN → IN_PROGRESS` | `active_members ≥ team_size_min` | بستن پذیرش، فعال‌سازی مراحل |
| `IN_PROGRESS → COMPLETED` | همهٔ `milestones.is_required` در وضعیت `APPROVED` + گزارش نهایی | صدور گواهی، امتیاز نهایی، درخواست بازتاب از اعضا |
| `→ PAUSED` | تصمیم مدیر با ذکر دلیل | توقف یادآوری‌ها، فریز شاخص سلامت |
| `PAUSED → OPEN` | تصمیم مدیر | **همیشه به `OPEN` برمی‌گردد، نه `IN_PROGRESS`**: حدس زدن وضعیت پیش از توقف ممکن نیست، چون مدیر همیشه عضو فعال است و «تیم دارد» سیگنالی نمی‌دهد. برای شروع دوبارهٔ کار، `POST /start`. |
| `→ CANCELLED` | تصمیم مدیر یا استاد | امتیاز مراحل تأییدشده **حفظ می‌شود** |

> **تصمیم مهم:** لغو پروژه امتیازهای کسب‌شده را پس نمی‌گیرد. دانشجو برای کاری
> که انجام داده امتیاز گرفته است؛ شکست پروژه تقصیر او نیست.

### شاخص سلامت (محاسبهٔ روزانه)

```python
def compute_health(project) -> Health:
    days_inactive = (today - project.last_activity_at).days
    overdue = count(m for m in project.milestones
                    if m.due_on < today and m.status != 'APPROVED')

    if days_inactive >= 14:
        return STALLED
    if overdue >= 1 or days_inactive >= 7:
        return AT_RISK
    if project.deadline_on and (project.deadline_on - today).days <= 7 \
       and progress_ratio(project) < 0.7:
        return AT_RISK
    return HEALTHY
```

`last_activity_at` با هر یک از این رویدادها به‌روز می‌شود: ارسال تحویل‌دادنی،
تغییر وظیفه، پیام در گفتگو، پیوستن عضو.

## ۷.۶ جریان مرحله و تحویل‌دادنی

```
 مرحله: PENDING ──(پروژه IN_PROGRESS)──► IN_PROGRESS
                                              │
                    عضو تحویل‌دادنی می‌فرستد   │
                                              ▼
                                      ┌──────────────┐
                                      │  SUBMITTED   │ (v1)
                                      └──────┬───────┘
                                             │ مدیر/منتور باز می‌کند
                                             ▼
                                      ┌──────────────┐
                                      │UNDER_REVIEW  │
                                      └──────┬───────┘
                       ┌─────────────────────┼─────────────────┐
                       ▼                     ▼                 ▼
                 ┌──────────┐    ┌────────────────────┐  ┌──────────┐
                 │ APPROVED │    │ CHANGES_REQUESTED  │  │ REJECTED │
                 └────┬─────┘    └─────────┬──────────┘  └──────────┘
                      │                    │ عضو نسخهٔ جدید می‌فرستد
                      │                    └──────► SUBMITTED (v2) ──┐
                      │                                    ▲         │
                      │                                    └─────────┘
                      ▼
          مرحله → APPROVED
          امتیاز ثبت می‌شود
          اعلان به تیم
          بررسی: آیا همهٔ مراحل الزامی تأیید شده؟ ──► پیشنهاد بستن پروژه
```

**قواعد:**
- نسخه‌ها هرگز پاک نمی‌شوند. بازبین می‌تواند نسخه‌های قبلی را ببیند.
- `CHANGES_REQUESTED` **باید** بازخورد متنی داشته باشد (اعتبارسنجی سرور).
- تحویل پس از مهلت مجاز است ولی `is_late` علامت می‌خورد و ضریب امتیاز ۰.۷ می‌گیرد (§09).
- یادآوری خودکار: ۳ روز و ۱ روز پیش از `due_on`، و ۱ روز پس از آن در صورت عدم تحویل.

## ۷.۷ چرخهٔ بلوغ کسب‌وکار

```
IDEA ──► VALIDATION ──► MVP ──► FIRST_REVENUE ──► GROWTH
                                                      │
        هر مرحله ──► PAUSED / CLOSED ◄────────────────┘
```

**معیارهای خروج هر مرحله (بررسی خودکار پیش از ارتقا):**

| از | به | معیار |
|----|-----|-------|
| `IDEA` | `VALIDATION` | شرح، مسئله، بازار هدف، و مدل درآمد پر شده باشد |
| `VALIDATION` | `MVP` | جمع مقدار `MEETINGS` و `LEADS` **تأییدشده** ≥ ۱۰ |
| `MVP` | `FIRST_REVENUE` | ≥ ۱ `Deliverable` تأییدشده از نوع `CODE` یا `MEDIA` در پروژه‌های کسب‌وکار (`projects.venture_id`) |
| `FIRST_REVENUE` | `GROWTH` | مجموع `SALES_AMOUNT` تأییدشده > آستانهٔ تنظیمات (`VENTURE_GROWTH_THRESHOLD_RIAL`، پیش‌فرض ۵۰۰ میلیون ریال) |

شاخص‌های پروژه‌های یک کسب‌وکار در معیارهای خود آن حساب می‌شوند. هر گذار یک
ردیف `venture_stage_changes` است؛ ارتقا به **همهٔ اعضای فعال** `50 × مرحله`
امتیاز می‌دهد و بازگشت از توقف امتیاز ندارد ([ADR-0014](../adr/0014-ideas-ventures-and-invitations.md)).

اگر معیار برقرار نباشد، `409 STAGE_CRITERIA_NOT_MET` با فهرست موارد کمبود
برگردانده می‌شود تا کاربر بداند دقیقاً چه چیزی لازم است.

## ۷.۸ جریان ارتقای ایده

```
 ایده ثبت می‌شود ──► OPEN ──► رأی و نظر جمع می‌کند
                        │
              استاد/مدیر ارتقا می‌دهد
                        │
            ┌───────────┴───────────┐
            ▼                       ▼
      Project ساخته شد        Venture ساخته شد
            │                       │
            └───────────┬───────────┘
                        ▼
          ideas.status = PROMOTED
          ideas.promoted_to_{type,id,by,at} پر می‌شود
          نویسنده: اعلان + امتیاز IDEA_PROMOTED (۱۰۰، جدول §9.2)
```

* **پروژه:** ارتقادهنده مدیر پروژهٔ `DRAFT` می‌شود؛ تیم همان لحظه ساخته
  می‌شود و نویسنده دعوت (`team_invitations`، منبع `IDEA_PROMOTION`) می‌گیرد.
* **کسب‌وکار:** نویسنده بنیان‌گذار می‌شود. ایدهٔ ناشناس به کسب‌وکار ارتقا
  نمی‌یابد (۴۰۹)، چون صفحهٔ کسب‌وکار بنیان‌گذار را نشان می‌دهد.

همه در یک تراکنش و با قفل ردیف ایده: دو ارتقای هم‌زمان، دو مقصد نمی‌سازند.

## ۷.۹ گردش‌کار هشت‌مرحله‌ای شهر هوشمند

این یک **الگوی پروژه** است: ساخت پروژهٔ نوع `C` با این الگو، هشت مرحله را
به‌صورت خودکار می‌سازد.

| # | مرحله | تحویل‌دادنی | چک‌لیست کیفیت |
|---|-------|-------------|----------------|
| ۱ | انتخاب محدوده | GeoJSON محدوده + توجیه انتخاب | محدوده بسته است؛ مساحت در بازهٔ مجاز؛ بدون هم‌پوشانی با پروژهٔ فعال |
| ۲ | استخراج OSM | فایل `.osm` خام + گزارش آمار شبکه | تعداد گره و یال ثبت شده؛ نسخهٔ OSM و تاریخ استخراج مشخص |
| ۳ | راستی‌آزمایی | جدول مغایرت + شواهد تصویری | هر مغایرت با ≥۲ منبع مستقل بررسی شده؛ بازدید میدانی برای موارد بحرانی |
| ۴ | مدل SUMO | `.net.xml` + `.rou.xml` + گزارش خطا | `netconvert` بدون خطا؛ اتصال شبکه بررسی شده؛ چراغ‌ها کدگذاری شده |
| ۵ | تخمین تقاضا | ماتریس مبدأ-مقصد + روش‌شناسی | منبع داده مستند؛ روش تخمین توجیه شده؛ اعتبارسنجی با شمارش موجود |
| ۶ | سناریوسازی | ≥۳ سناریو + نتایج شبیه‌سازی | سناریوی پایه دارد؛ شاخص‌ها (تأخیر، صف، انتشار) گزارش شده |
| ۷ | گزارش مدیریتی | PDF ≤۲۰ صفحه، فارسی، بدون ژارگون | خلاصهٔ اجرایی یک‌صفحه‌ای؛ توصیهٔ عملی مشخص؛ برآورد هزینه |
| ۸ | داشبورد شهرداری | داشبورد تعاملی + راهنما | روی موبایل کار می‌کند؛ بدون آموزش قابل استفاده؛ داده قابل به‌روزرسانی |

**پیاده‌سازی ([ADR-0016](../adr/0016-city-lab-workflow-template.md)):** الگو محتوای کد است (`silp.domain.city`) و فقط برای نوع C. هر مرحله مسئول دارد (پیش‌فرض مدیر، `milestones.owner_id`)، بارم‌ها روی هم ۵۰۰ امتیاز و مدت‌ها ۱۶ هفته است. مرحلهٔ n فقط پس از تأیید n−۱ تحویل می‌پذیرد (`CITY_STAGE_LOCKED`). هر مورد چک‌لیست یا خودکار است (سامانه می‌سنجد: بسته بودن و مساحت محدوده ۰٫۰۵ تا ۳۰ کیلومتر مربع، صفر بودن خطای netconvert، دو منبع برای هر مغایرت، سناریوی پایه، ≤۲۰ صفحه) یا دستی (تحویل‌دهنده تیک می‌زند و بازبین داوری می‌کند)؛ همهٔ کمبودها یک‌جا برمی‌گردند. هم‌پوشانی محدوده با پروژهٔ فعال دیگر هشدار است، نه ممنوعیت (FR-CITY-02). هر `.osm`، `.net.xml` و `.rou.xml` نسخهٔ بعدی همان نوع در کتابخانهٔ پروژه است و «نسخهٔ جاری» آخرین تأییدشده. تأیید مرحلهٔ ۸ گردش‌کار را کامل می‌کند (`workflow_completed_at`، نشان «شهرساز»).

**قاعدهٔ حیاتی مرحلهٔ ۳:** راستی‌آزمایی OSM بدون شواهد تصویری تأیید نمی‌شود.
دادهٔ OSM ایران ناقص است و مدل ساخته‌شده روی دادهٔ خام، بی‌ارزش است. این
سخت‌گیری عمدی است.

## ۷.۱۰ گردش‌کار اعلان (Outbox)

```
 رویداد دامنه رخ می‌دهد (مثلاً تحویل‌دادنی تأیید شد)
              │
              ▼
  ┌───────────────────────────────┐
  │ در همان تراکنش دیتابیس:        │
  │  ۱. تغییر وضعیت موجودیت       │
  │  ۲. INSERT notifications      │
  │  ۳. INSERT outbox_messages    │
  │     برای هر کانال فعال کاربر  │
  └───────────────┬───────────────┘
                  │ COMMIT
                  ▼
      ┌───────────────────────┐
      │ کارگر ARQ هر ۵ ثانیه: │
      │ SELECT … FOR UPDATE   │
      │ SKIP LOCKED LIMIT 50  │
      └───────────┬───────────┘
                  ▼
           ارسال به ارائه‌دهنده
                  │
        ┌─────────┼─────────┐
        ▼                   ▼
     موفق                 ناموفق
        │                   │
        ▼                   ▼
     SENT           attempts += 1
                    next_attempt_at = now +
                      (2^attempts × 30s ± jitter)
                            │
                    attempts ≥ 5؟
                            │
                            ▼
                          DEAD
                     (هشدار به مدیر)
```

**قواعد:**
- ساعت آرام (۲۳ تا ۸ **به وقت تهران**): پیام‌های غیر `URGENT` تا ۸ صبح به
  تعویق می‌افتند — در تلاش مجدد هم.
- شکست یک کانال، ارسال بقیهٔ کانال‌ها را متوقف نمی‌کند (رکوردهای مستقل).
- `SKIP LOCKED` امکان اجرای چند کارگر موازی را بدون تداخل می‌دهد.
- پیام `DEAD` به‌صورت دستی از `/admin/outbox` قابل تلاش مجدد است.
- **اجاره (ADR-0013):** برداشتن پیام `status = SENDING` و
  `next_attempt_at = now + ۵ دقیقه` می‌گذارد و commit می‌کند؛ ارسال بیرون
  از تراکنش است؛ نتیجه فقط اگر `attempts` عوض نشده باشد نوشته می‌شود.
  کارگری که وسط ارسال بمیرد، پیام را پس از پایان اجاره آزاد می‌کند.
- شکست **دائمی** (گیرندهٔ نامعتبر، الگوی ناموجود، ربات بسته‌شده) بی‌درنگ
  `DEAD` است. هشدار مدیر روزی یک اعلان است.
- متن هنگام **ارسال** از الگو ساخته می‌شود؛ ویرایش الگو روی پیام‌های در صف
  هم اثر دارد.

## ۷.۱۲ همزمانی، شمارنده‌ها و شماره‌گذاری

این بخش منبع رایج‌ترین باگ‌های ظریف است. هر مورد راه‌حل صریح دارد.

### ساخت خودکار تیم

تیم **به‌صورت خودکار** هنگام گذار `DRAFT → OPEN` ساخته می‌شود، نه هنگام پذیرش
اولین عضو. دلیل: `team_members` باید همیشه یک `team_id` معتبر داشته باشد و
مدیر پروژه از لحظهٔ انتشار، عضو `is_lead` است.

```
publish_project():
  در یک تراکنش:
    ۱. projects.status = 'OPEN'
    ۲. INSERT teams (project_id, name = project.title_fa)
    ۳. INSERT team_members (team_id, user_id = project.lead_id, is_lead = true)
    ۴. انتشار رویداد ProjectPublished
```

> `lead_id` در شمارش `team_size_max` **حساب می‌شود**. پروژه‌ای با `team_size_max = 3`
> یعنی مدیر + دو نفر دیگر. این باید در متن رابط کاربری روشن باشد.

### شماره‌گذاری `attempt_no` و `version`

هر دو در معرض شرایط رقابتی‌اند. راه‌حل: **قید یکتا + تلاش مجدد**، نه
`SELECT MAX(...) + 1` خام.

```python
async def next_sequence(session, *, insert_stmt, max_retries: int = 3):
    """درج با شمارهٔ بعدی؛ در صورت تصادم، دوباره تلاش می‌کند."""
    for attempt in range(max_retries):
        try:
            async with session.begin_nested():
                return await session.execute(insert_stmt)
        except UniqueViolationError:
            if attempt == max_retries - 1:
                raise ConcurrentModification()
            continue
```

قیدهای یکتای پشتیبان (در §04 تعریف شده‌اند):
`quiz_attempts (quiz_id, student_id, attempt_no)` ·
`deliverables (milestone_id, submitter_id, version)`

برای `quiz_attempts` یک قید دوم هم هست که از تلاش هم‌زمان جلوگیری می‌کند:
ایندکس جزئی یکتای `idx_one_active_attempt`. این یعنی دو کلیک سریع روی
«شروع آزمون» فقط یک تلاش می‌سازد — دومی خطای `ACTIVE_ATTEMPT_EXISTS` می‌گیرد.

### شمارنده‌های غیرنرمال

| ستون | نگهداری | چرا |
|------|---------|-----|
| `ideas.vote_count` | تریگر روی `idea_votes` | جلوگیری از `COUNT(*)` در هر بار نمایش فهرست |
| `ideas.comment_count` | تریگر روی `idea_comments` | همان |
| `quizzes.total_points` | تریگر روی `quiz_questions` | نمایش در فهرست آزمون‌ها |
| `project_roles.filled` | **لایهٔ سرویس، نه تریگر** | منطق پیچیده‌تر است (وضعیت عضو، نقش خالی) |
| `qa_replies.helpful_count` | تریگر | — |

```sql
CREATE OR REPLACE FUNCTION bump_idea_votes() RETURNS TRIGGER AS $$
BEGIN
  IF TG_OP = 'INSERT' THEN
    UPDATE ideas SET vote_count = vote_count + 1 WHERE id = NEW.idea_id;
  ELSIF TG_OP = 'DELETE' THEN
    UPDATE ideas SET vote_count = GREATEST(0, vote_count - 1) WHERE id = OLD.idea_id;
  END IF;
  RETURN NULL;
END;
$$ LANGUAGE plpgsql;
```

**کار بازسازی:** یک کار ماهانهٔ `reconcile_counters` شمارنده‌ها را با شمارش
واقعی مقایسه و در صورت انحراف اصلاح و لاگ می‌کند. تریگرها گاهی در مهاجرت‌ها
یا درج انبوه دور زده می‌شوند.

### ظرفیت پروژه تحت رقابت

پذیرش هم‌زمان دو درخواست می‌تواند ظرفیت را بشکند. راه‌حل: قفل سطر پروژه.

```sql
BEGIN;
SELECT team_size_max FROM projects WHERE id = :pid FOR UPDATE;
-- شمارش اعضای فعال، بررسی ظرفیت، درج عضو
COMMIT;
```

### امتیاز آزمون و «بهترین تلاش»

قاعدهٔ `QUIZ_SCORE` فقط برای **بهترین تلاش** امتیاز می‌دهد (§9.8). چون دفتر کل
تغییرناپذیر است، وقتی تلاش دوم بهتر از اول باشد:

```
۱. رکورد امتیاز تلاش قبلی را با reverse() معکوس کن
۲. امتیاز جدید را با source_id = تلاش جدید ثبت کن
۳. هر دو در یک تراکنش
```

کلید بی‌اثری روی `(user, rule, source_type, source_id)` است و چون `source_id`
متفاوت است، تصادم نمی‌کند. رکورد معکوس `reverses_id` دارد پس از قید یکتا
مستثناست (شرط `WHERE reverses_id IS NULL`).

### وضعیت `OVERDUE` مراحل

در §4.6 وجود دارد ولی کار پس‌زمینه‌اش در فهرست §7.11 نبود. افزوده می‌شود:

```
mark_overdue_milestones — روزانه ساعت ۱ بامداد
UPDATE milestones SET status = 'OVERDUE'
WHERE due_on < CURRENT_DATE
  AND status IN ('PENDING','IN_PROGRESS')
  AND NOT EXISTS (SELECT 1 FROM deliverables d
                  WHERE d.milestone_id = milestones.id
                    AND d.status IN ('SUBMITTED','UNDER_REVIEW','APPROVED'));
```

`OVERDUE` مانع ارسال تحویل‌دادنی **نیست** — فقط علامت‌گذاری است و ضریب
تأخیر ۰.۷ (§9.3) را فعال می‌کند.
