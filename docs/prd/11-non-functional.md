## ۱۱.۱ امنیت

### NFR-01 · حفاظت از داده‌های شخصی

| داده | طبقه‌بندی | حفاظت |
|------|-----------|-------|
| کد ملی | **حساس** | رمزنگاری AES-256 با `pgcrypto`، کلید در متغیر محیطی جدا از دیتابیس. ستون هش برای بررسی یکتایی. هرگز در لاگ، پاسخ API، یا خروجی Excel. |
| موبایل و ایمیل | **محرمانه** | ذخیرهٔ ساده، اما در پاسخ‌های عمومی همیشه پوشانده: `0912***4567` |
| رمز عبور | **حساس** | `argon2id` با `time_cost=3, memory_cost=65536, parallelism=4` |
| OTP | **حساس** | `bcrypt`، حذف فیزیکی پس از ۲۴ ساعت |
| توکن refresh | **حساس** | `sha256` |
| نمرات | **محرمانه** | فقط صاحب نمره و استاد مربوطه |
| پاسخ‌های آزمون | **محرمانه** | فقط صاحب و مصحح |

**کمینه‌سازی داده:** کد ملی اختیاری است و تنها در صورتی درخواست می‌شود که برای
صدور گواهی رسمی لازم باشد. فیلدی که استفاده نمی‌شود، جمع‌آوری نمی‌شود.

### NFR-02 · جلوگیری از آسیب‌پذیری‌های رایج

| تهدید | دفاع |
|-------|------|
| SQL Injection | فقط SQLAlchemy با پارامتر مقید. `text()` خام ممنوع مگر با بازبینی دونفره. |
| XSS | React به‌صورت پیش‌فرض escape می‌کند. `dangerouslySetInnerHTML` ممنوع؛ محتوای Markdown با `rehype-sanitize`. |
| CSRF | توکن در هدر `Authorization` (نه کوکی) ⇒ CSRF موضوعیت ندارد. اگر کوکی لازم شد: `SameSite=Strict` + توکن CSRF. |
| IDOR | هر endpoint مالکیت/عضویت را بررسی می‌کند (§06). تست خودکار اجباری. |
| بارگذاری فایل مخرب | بررسی Magic Number، محدودیت نوع و حجم، ذخیره خارج از ریشهٔ وب، اسکن ClamAV، سرو با `Content-Disposition: attachment` |
| SSRF | فیلد URL خارجی (لینک پروژه، DOI) اعتبارسنجی: فقط `http(s)`، بدون IP خصوصی، بدون `localhost` |
| Open Redirect | پارامتر `next` فقط مسیر نسبی می‌پذیرد |
| نشت زمانی (Timing) | مقایسهٔ توکن و OTP با `secrets.compare_digest` |
| Enumeration | پیام یکسان برای «کاربر نیست» و «رمز غلط»؛ زمان پاسخ یکنواخت |
| Brute force | محدودیت نرخ + قفل نرم + CAPTCHA پس از ۳ شکست |

### NFR-03 · هدرهای امنیتی

```nginx
add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
add_header X-Content-Type-Options "nosniff" always;
add_header X-Frame-Options "DENY" always;
add_header Referrer-Policy "strict-origin-when-cross-origin" always;
add_header Permissions-Policy "camera=(), microphone=(), geolocation=(self)" always;
add_header Content-Security-Policy "default-src 'self'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob: ${SILP_S3_ORIGIN}; font-src 'self'; connect-src 'self' ${SILP_S3_ORIGIN}; media-src 'self' ${SILP_S3_ORIGIN}; frame-ancestors 'none'; base-uri 'self'; form-action 'self'; object-src 'none'" always;
```

**M7-17 (ADR-0018):** نسخهٔ پیشین `script-src 'nonce-…'` بود؛ App Router دادهٔ
RSC را با اسکریپت درون‌خطی بی‌nonce می‌فرستد و پشت nginx واقعی فرم ورود اصلاً
ساخته نمی‌شد. nonce در Next فقط با رندر پویای همهٔ صفحه‌ها ممکن است؛
`'unsafe-inline'` برای script پذیرفته شد و هیچ جای برنامه HTML کاربر را خام
رندر نمی‌کند. `connect-src` مبدأ فضای ذخیره‌سازی را دارد (بارگذاری مستقیم
مرورگر به S3). هدرها در `infra/nginx/templates/security-headers.inc.template`اند
و در هر location که خودش `add_header` دارد دوباره include می‌شوند.

## ۱۱.۳ قابلیت اطمینان

### NFR-09 · دسترس‌پذیری

| معیار | هدف |
|-------|-----|
| دسترس‌پذیری ماهانه | ۹۹.۵٪ (≈ ۳.۶ ساعت قطعی مجاز) |
| دسترس‌پذیری در بازهٔ آزمون | ۹۹.۹٪ |
| RPO (حداکثر داده از دست‌رفته) | ۱۵ دقیقه |
| RTO (حداکثر زمان بازیابی) | ۲ ساعت |

**پنجرهٔ نگهداری:** جمعه‌ها ۳ تا ۵ بامداد، با اعلان ۴۸ ساعت قبل. هرگز در هفتهٔ
امتحانات.

### NFR-10 · پشتیبان‌گیری

| نوع | تناوب | نگهداری | محل |
|-----|-------|---------|-----|
| WAL پیوسته | لحظه‌ای | ۷ روز | فضای ابری جدا |
| کامل دیتابیس | روزانه ۴ بامداد | ۳۰ روز | فضای ابری جدا |
| کامل ماهانه | ماهانه | ۱۲ ماه | فضای ابری جدا + نسخهٔ آفلاین |
| فایل‌ها (S3) | همگام‌سازی روزانه | ۳۰ روز | باکت جدا |

**الزام حیاتی:** آزمون بازیابی **ماهانه**. پشتیبانی که بازیابی‌اش آزمایش نشده،
پشتیبان نیست. نتیجهٔ هر آزمون در `docs/ops/restore-drills.md` ثبت می‌شود.

**پیاده‌سازی (M7-17، M7-18):** کانتینر `backup` از ایمیج `postgres:16` (نه ایمیج
API که `pg_dump` ۱۵ دارد)؛ «کامل روزانه» دو پشتیبان است: منطقی (`pg_dump`، با
sha256 و شمار ردیف جدول‌ها) و پایهٔ فیزیکی (`pg_basebackup`) که بازیابی نقطه‌ای
با WAL بدون آن ممکن نیست. `archive_timeout = 900` تا RPO در ساعت کم‌ترافیک هم
۱۵ دقیقه بماند. رویه‌ها در `docs/ops/runbook.md`؛ اولین آزمون (منطقی و نقطه‌ای)
در `restore-drills.md`.

### NFR-11 · تاب‌آوری

| سناریو | رفتار مورد انتظار |
|--------|-------------------|
| Redis از کار بیفتد | اپ کار می‌کند، کندتر. کش اختیاری است، نه حیاتی. |
| S3 در دسترس نباشد | آپلود خطا می‌دهد با پیام روشن؛ بقیهٔ سامانه سالم |
| ارائه‌دهندهٔ پیامک قطع شود | پیام در `outbox` می‌ماند، بازپخش خودکار (D-08) |
| تلگرام مسدود شود | کانال علامت `DEGRADED`، بقیهٔ کانال‌ها کار می‌کنند |
| دیتابیس کند شود | مهلت کوئری ۱۰ ثانیه، خطای صریح به‌جای انتظار نامحدود |
| قطع اینترنت دانشجو در آزمون | پاسخ‌ها در `localStorage`، همگام‌سازی خودکار (§07) |

### NFR-12 · مدیریت خطا

- هیچ Stack Trace به کاربر نمایش داده نمی‌شود.
- هر خطای ۵۰۰ یک `trace_id` دارد که در لاگ و پاسخ یکسان است.
- خطاهای مورد انتظار (`409`, `422`) در سطح `INFO` لاگ می‌شوند، نه `ERROR` —
  تا سیگنال واقعی در نویز گم نشود.

## ۱۱.۴ رصدپذیری

### NFR-13 · لاگ

- قالب **JSON ساختاریافته**، نه متن آزاد.
- فیلدهای اجباری: `timestamp`, `level`, `trace_id`, `user_id`, `route`, `duration_ms`
- **هرگز لاگ نمی‌شود:** رمز، توکن، OTP، کد ملی، پاسخ آزمون، محتوای پیام
- سطوح: `DEBUG` فقط توسعه · `INFO` رویداد کسب‌وکار · `WARN` وضعیت غیرعادی
  قابل بازیابی · `ERROR` نیازمند بررسی

### NFR-14 · معیارها

```
# کسب‌وکار
silp_users_registered_total
silp_survey_completed_total{step}
silp_applications_submitted_total{result}
silp_milestones_approved_total
silp_points_awarded_total{category}
silp_quiz_attempts_active          ← گیج زنده

# فنی
http_request_duration_seconds{route, method, status}
db_query_duration_seconds{operation}
outbox_queue_depth{channel, status}
outbox_delivery_total{channel, result}
cache_hit_ratio{key_prefix}
background_job_duration_seconds{task}
background_job_failures_total{task}
silp_background_job_last_success_timestamp_seconds{task}
```

**M7-17 (ADR-0018):** برچسب کار `task` است نه `job` — `job` برچسب هدف خود
Prometheus است و برچسب هم‌نام به `exported_job` تغییر نام می‌داد. معیارهای
کسب‌وکار و صف هنگام خراش از PostgreSQL خوانده می‌شوند (نه شمارندهٔ
درون‌فرایندی)؛ `cache_hit_ratio` و `db_query_duration_seconds` هنوز ساخته
نشده‌اند و جای دومی `silp_db_connections{state}` است. `/metrics` در تولید
`METRICS_TOKEN` می‌خواهد و از nginx عبور نمی‌کند؛ قواعد NFR-15 در
`infra/monitoring/alerts.yml` با آزمون `promtool`.

### NFR-18 · معماری کد

```
لایه‌بندی اجباری — وابستگی فقط رو به پایین:

  routers/      ← HTTP، اعتبارسنجی ورودی، فراخوانی سرویس
      ↓
  services/     ← منطق کسب‌وکار، تراکنش، انتشار رویداد
      ↓
  repositories/ ← دسترسی به داده، کوئری
      ↓
  models/       ← موجودیت‌های SQLAlchemy
```

- `routers` هرگز مستقیم به `models` دسترسی ندارد.
- `services` هرگز به `Request` یا `Response` وابسته نیست (تا از CLI و کار
  پس‌زمینه هم قابل فراخوانی باشد).
- منطق دامنهٔ خالص (`scorer.py`، `learning_score.py`) بدون I/O.

## ۱۱.۶ حریم خصوصی و انطباق

### NFR-20 · اصول

۱. **کمینه‌سازی:** فقط داده‌ای که برای عملکرد مشخصی لازم است.
۲. **شفافیت:** کاربر در `/me/settings` می‌بیند چه داده‌ای داریم و کجا استفاده می‌شود.
۳. **کنترل:** خروجی داده (JSON) و درخواست حذف حساب از رابط کاربری.
۴. **پیش‌فرض خصوصی:** نیمرخ پیش‌فرض **خصوصی** است؛ عمومی‌سازی انتخاب فعال کاربر.
۵. **رضایت آگاهانه:** استفادهٔ پژوهشی از داده‌های تجمیعی، با اطلاع و امکان انصراف.

### NFR-21 · حذف حساب

```
درخواست کاربر
   ↓ (۳۰ روز مهلت انصراف، با اعلان)
ناشناس‌سازی:
   • حذف: موبایل، ایمیل، کد ملی، آواتار، نام
   • جایگزینی نام با «کاربر حذف‌شده»
   • حفظ: امتیازها، تحویل‌دادنی‌ها، مشارکت در پروژه (بدون هویت)
   • حفظ: لاگ حسابرسی (الزام قانونی)
```

داده‌های تیمی پاک نمی‌شوند چون به کار دیگران گره خورده‌اند — اما هویت جدا می‌شود.

| واقعیت | پاسخ طراحی |
